# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 1. 적용 기준

### 반드시 TDD를 적용한다

- **비즈니스 로직**: 조건 분기, 계산, 상태 전이
- **API**: 요청 검증, 응답 형식, 에러 처리
- **유틸 함수**: 변환, 파싱, 포매팅 등 순수 함수
- **버그 수정**: 버그를 재현하는 실패 테스트를 먼저 작성한 뒤 고친다

### TDD가 불필요하다

- **타입 정의**: `interface`, `type` 선언
- **설정 파일**: `vite.config.ts`, `tsconfig`, `eslint.config.js` 등
- **순수 UI**: 로직 없이 마크업/스타일만 있는 컴포넌트
- **SQL**: 스키마, 마이그레이션, 단순 쿼리

판단이 애매하면 **적용 대상으로 간주한다.**

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에서 여러 동작을 검증하지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 눈으로 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류, 잘못된 셋업으로 실패했다면 테스트를 고쳐 다시 RED를 확인한다.

### GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 아직 테스트가 요구하지 않는 기능, 옵션, 확장 포인트를 미리 만들지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 실행으로 확인한다.

### REFACTOR: 구조 개선

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지한다.** 수정할 때마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 요구된 모든 동작이 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 재시작한다.**

- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해 두고 다시 쓰기 모두 포함한다.
- 삭제한 코드를 복사해 붙여넣지 않는다. 테스트가 요구하는 만큼만 새로 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드도 깨진다. 테스트는 30초면 쓴다. 단순할수록 비용이 낮으니 안 쓸 이유가 없다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 이미 통과한다. 실패를 본 적 없는 테스트는 아무것도 증명하지 못한다. |
| "시간이 없다" | 테스트 없이 만든 코드의 디버깅과 재작업이 더 오래 걸린다. 급할수록 사이클을 지킨다. |
| "삭제하면 낭비" | 이미 쓴 시간은 매몰 비용이다. 검증 안 된 코드를 유지하는 것이 더 큰 낭비다. |
| "프로토타입이다" | 프로토타입은 곧 프로덕션이 된다. 버릴 코드라면 어차피 아깝지 않으니 삭제도 쉽다. |

## 5. 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그것을 우선한다.**
- **이 파일은 기본값(fallback)** 이다. 프로젝트 규칙이 침묵하는 부분에만 적용한다.
- 충돌 시 프로젝트 규칙을 따르고, 이 파일의 해당 조항은 무시한다.
