# commit

변경사항을 분석하고 논리적 단위로 나누어, 한국어 컨벤션 커밋 메시지로 커밋하는 스킬.

## 트리거

- "커밋", "커밋해줘", "변경사항 저장해줘" 등의 요청
- `/commit`

## 절차

### 1. 변경사항 분석

다음 명령으로 현재 상태를 파악한다.

```bash
git status
git diff            # unstaged 변경
git diff --staged   # staged 변경
git log --oneline -10   # 기존 커밋 스타일 참고 (커밋이 있는 경우)
```

- untracked 파일은 내용을 직접 읽어 성격을 파악한다.
- `.env`, 키, 토큰 등 비밀 정보나 `node_modules`, 빌드 산출물이 포함되어 있으면 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

- 하나의 목적(기능 추가, 버그 수정, 리팩터링, 설정 변경 등)을 가진 변경끼리 묶는다.
- 서로 다른 목적의 변경은 별도 커밋으로 분리한다.
- 각 커밋에 포함할 파일 목록을 정리한다.

### 3. 커밋 메시지 작성

형식: `타입: 요약` (한국어)

| 타입 | 용도 |
|------|------|
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 코드 구조 개선 |
| chore | 빌드, 설정, 의존성, 기타 잡무 |

규칙:
- 요약은 50자 내외, 마침표 없이 간결하게 작성한다.
- "무엇을, 왜" 변경했는지 드러나게 쓴다.
- 필요하면 빈 줄 뒤에 본문으로 상세 설명을 덧붙인다.
- 예: `feat: 컴포넌트 생성 API 엔드포인트 추가`

### 4. 커밋 실행

사용자 승인 절차 없이 바로 커밋한다.

- 단위별로 파일을 명시적으로 `git add <파일>` 한 뒤 `git commit` 한다. (`git add -A`, `git add .` 지양)
- 커밋 메시지 끝에는 시스템이 지정한 Co-Authored-By 등 attribution 줄을 포함한다.
- hook이 실패하면 `--no-verify`로 우회하지 말고 원인을 해결한다.
- 완료 후 `git log --oneline`으로 커밋 단위, 파일 목록, 메시지를 사용자에게 보고한다.

## 주의

- push는 사용자가 명시적으로 요청한 경우에만 한다.
- 기존 커밋을 amend하거나 force 옵션을 쓰지 않는다.
